# P13 load harness

Run on disposable, isolated local infrastructure only. These scripts mutate data, generate orders and financial/inventory ledger entries, and write bearer tokens. Never point them at production. Do not run profiles concurrently or alongside other heavy tests. Keep the generated credentials private and outside version control. The ordinary development seed is not a sufficient checkout or GPS dataset.

The harness uses Grafana k6 v1.3.0, Linux x86-64, installed by `test/load/install-k6.sh`. The pinned SHA-256 `84d26fc1f7bc03e02f2e016b3b1b20c032e05dfe461fca82de4e3a6ebe72ddbd` comes from [Grafana's release checksums](https://github.com/grafana/k6/releases/download/v1.3.0/k6-v1.3.0-checksums.txt). The socket profile uses the project's socket.io-client. k6 and the application should be separate processes; the load generator should have sufficient CPU and network capacity. Results cannot distinguish generator saturation from server saturation unless both are monitored.

Prepare a migrated database and run `scripts/seed.ts`, then set `NODE_ENV=test`, `AUTH_PROVIDER=local`, `DATABASE_URL`, `LOCAL_JWT_SECRET`, `LOAD_FIXTURES=yes` and `LOAD_FIXTURE_FILE` (inside an existing directory). Run `node --import tsx test/load/fixtures.ts` once on a fresh isolated database. This adds 1,300 wallet-funded customers, 100 riders, and 1,000 receipt-backed units per SKU at the first of the three stores. It is deliberately non-reentrant: a second run fails on duplicate identities, avoiding silent fixture reuse. Use disjoint `CHECKOUT_OFFSET` ranges for each checkout mode, because successful checkouts change customer carts and stock. The local fixture provides two sets of 600 customers with a gap for k6 boundary iterations. Verify fixture-to-ledger reconciliation and completed-order funding after every run; a successful latency result alone is not acceptance.

Both fixture seeders explicitly set the load-only `storeBacklogPauseThreshold` to 20,000: checkout creates pick tasks without running pickers, so the default threshold of 100 would automatically pause the store. This does not test the default auto-pause behavior; cover that separately. The local runner reports the override.

Set the application load-only limits explicitly (for example `RATE_LIMIT_DEFAULT_PER_MIN=10000`, `RATE_LIMIT_SEARCH_PER_MIN=10000`, `RATE_LIMIT_LOCATION_PER_MIN=10000`) and record their values in the invoking environment. These settings remove default per-identity throttling for load measurements; test default abuse limits separately. Run audience instances with the same database, Redis, and local JWT secret.

- `LOAD_PROFILE=local BASE_URL=... CUSTOMER_TOKEN=... ADDRESS_ID=... test/load/run-catalog.sh`: catalog 20/s and search 10/s for 5 minutes. It enforces p95 at 300/500 ms, errors below 0.1%, zero dropped iterations and minimum requested counts. Token and address must belong to the same seeded customer.
- `LOAD_PROFILE=local LOAD_KIND=checkout CHECKOUT_MODE=distributed|hot BASE_URL=... LOAD_FIXTURE_FILE=... test/load/run-http.sh`: 2 completed wallet-funded checkouts/s for 5 minutes; p95 <= 1 s measures cart, quote and place end to end. Run each mode with fresh fixtures. All errors fail the common threshold; this profile does not classify any conflict as expected.
- `LOAD_PROFILE=local LOAD_KIND=gps BASE_URL=... LOAD_FIXTURE_FILE=... test/load/run-http.sh`: 20 updates/s over 100 riders for 5 minutes, p95 <= 200 ms. Every point must be accepted and persisted; each successive point per rider moves about 55 m to force distance sampling.
- `LOAD_PROFILE=local RIDER_URL_1=... RIDER_URL_2=... REDIS_URL=... LOAD_FIXTURE_FILE=... node test/load/sockets.mjs`: 500 authenticated rider Socket.IO connections split across two instances for 5 minutes. The harness publishes to the application's Redis broadcast channel and verifies per-socket deliveries and p95 <= 1 s. It does not exercise customer order rooms. Socket connection snapshots are required before publishing.
- `LOAD_PROFILE=local LOAD_ISOLATED_DATABASE=yes DATABASE_URL=... REDIS_URL=... node --import tsx test/load/outbox.ts`: uses a **separate migrated database** with no other relay and an empty backlog. It produces 20 transactional events/s for 5 minutes, stops and restarts its real BullMQ worker/relay while production continues, then checks backlog recovery and exactly-once processing. Worker concurrency defaults to 4 and the relay poll interval defaults to 500 ms; `QUEUE_CONCURRENCY` and `OUTBOX_POLL_INTERVAL_MS` can override them and are recorded. Healthy latency runs from an event timestamp just before its append transaction commits through consumer transaction completion, so it includes commit delay; it excludes the interruption and a recovery window of the same length. The completion measurement is stricter than measuring consumer start; p95 <= 2 s. The producer/worker are exercised directly, not through a business API.
- `RUN_SUBSCRIPTION_DISTRIBUTED_LOAD=1 pnpm test:int --testPathPatterns p13-distributed-load --runInBand`: separate 10,000-order generation case with domain-backed opening inventory and wallet credits, a 15-minute limit, replay checks, and wallet/inventory ledger reconciliation. It starts its own test containers. Its stock and funding setup differs from the historical baseline case, which remains unchanged.

`node --import tsx test/load/run-local.ts --profile=smoke` runs the isolated, sequential wiring suite using fresh containers and cleans up its own services; use `--profile=local` for the five-minute profiles. Both modes leave the 10,000-order subscription case to be run separately. The runner installs the pinned k6 if missing and retains reports and service logs.

For the AWS SQS outbox path, use `AWS_PROFILE=default AWS_P13_INTEGRATION=yes LOAD_ISOLATED_DATABASE=yes LOAD_PROFILE=smoke node --env-file-if-exists=.env --import tsx test/load/aws-outbox.ts`. It creates and migrates a disposable Aurora database, creates dedicated temporary SQS queues, runs a worker interruption and reconciliation check, and attempts to remove its test resources. This queue path does not use Valkey, so its fixture does not connect to or test the cache. Use `LOAD_PROFILE=local` for the five-minute, 20-events-per-second profile, run it without competing workloads, and separately record AWS resource usage. The smoke profile verifies recovery and reconciliation but does not enforce the latency threshold; it is a wiring check, not acceptance. A failed queue deletion leaves an ignored cleanup manifest in `artifacts/`.

The AWS runner warms 20 distinct IAM/TLS database connections before the measured producer starts and records that warm-up. `LOAD_POOL_MAX` can set a pool size from 1 to 64 for a separately reported tuning run; the throughput and latency targets remain unchanged. Its results describe steady-state behavior and do not establish cold-start performance; keep the earlier failed reports separately.

`LOAD_PROFILE=smoke` gives a clearly named 3-second wiring check and is not acceptance. Summaries, exit codes, generator resource measurements, and failed runs are retained under `artifacts/p13-load`. The HTTP wrappers require `/usr/bin/time` and Node on PATH. Fixtures hold tokens; do not upload them with reports. Threshold violations and missing datasets fail nonzero. Application CPU/memory, database/Redis resource usage, database invariants, and expected-conflict counts require separate monitoring/checks and must be included in acceptance evidence.

## Full staging handoff, not run

The original full staging target requires 100 stores with 20,000 eligible SKUs each (2 million store/SKU combinations); catalog 200/s and search 100/s; checkout 20/s for 15 minutes; and 5,000 riders/sockets plus 1,000 GPS updates/s for 30 minutes. Use `LOAD_FIXTURES=staging LOAD_ISOLATED_DATABASE=yes node --import tsx test/load/staging-fixtures.ts` after the normal development seed on a dedicated local-auth database; its defaults create 100 new stores, 20,000 SKUs per store, 18,100 funded customers and 5,000 riders. This writes structural data in batches and posts each stock receipt through the inventory service; two million receipts can take a long time and require substantial database capacity. The optional LOAD_STORES, LOAD_SKUS_PER_STORE, LOAD_CUSTOMERS, LOAD_RIDERS and LOAD_STOCK_PER_SKU variables are for explicitly sized test fixtures only and must retain default staging targets for acceptance. Validate counts and ledger invariants after preparation. It requires application resource monitoring and coordinated execution. Existing local fixtures do not meet these requirements: staging HTTP scripts reject insufficient datasets and the local outbox script offers no staging profile. Do not treat any local or smoke result as a full staging result. The staging owner must provision and validate the larger dataset, establish any simultaneous workload requirements, execute the full targets, reconcile invariants, and retain their results.
