# Current API contracts

Run `pnpm openapi:export` to generate and validate four OpenAPI 3.1 documents in `openapi/`. Development docs are available under `/v1/{customer|rider|store|admin}/docs` for enabled audiences. Production docs are disabled. The [operation manifest](manifests/operations.json) records the canonical implemented paths, permissions and evidence; future-phase entries remain explicitly planned.

Authentication uses audience-bound access tokens. Customer bootstrap alone accepts an ID token. A token from the wrong pool/client/audience is rejected with 401; an authenticated wrong role is rejected with 403; owner/store-scoped resource reads do not reveal another actor's records. Local `/dev/auth/token` and signed private-media capability routes are excluded from production API documents.

Requests use camelCase JSON and bounded, whitelist-only DTOs. Administrative lists use bounded cursor pages; the customer's address list is bounded by its configured address limit. Unknown DTO fields are rejected. Personal responses have `Cache-Control: no-store`. `X-Request-Id` is generated or validated, returned to clients and used as the problem response's trace ID.

Errors have content type `application/problem+json` and fields `type`, `title`, `status`, `code`, `detail`, `traceId`. Declared application codes survive serialization; arbitrary vendor messages, SQL and credentials do not. Relevant examples include `INVALID_TOKEN`, `PROFILE_NOT_INITIALIZED`, `ACCOUNT_DISABLED`, `RIDER_NOT_APPROVED`, `LAST_SUPER_ADMIN`, `APPROVAL_INVALID`, `CONCURRENT_MODIFICATION`, `ADDRESS_NOT_FOUND`, `RESOURCE_CONFLICT`, and `RATE_LIMITED`.

HTTP body/transport errors use the same envelope. Rate limits return `Retry-After`; ordinary requests fail open with a warning if Redis limits cannot be checked, while location ingestion is configured to fail closed. Per-actor limits run only after cryptographic identity verification; a broader per-IP limit protects anonymous ingress.

The idempotency primitive scopes a key to actor/audience/method/resource, hashes normalized input and fences active execution. Completed cached responses are replayed; changed input conflicts. Compact operation references remain after response pruning. Future money/stock endpoints must use this primitive plus their durable business-reference constraints.

Money in commerce contracts is integer paise serialized as decimal strings, never JSON floating point. Time is UTC in storage and IST for business windows. The P10–P12 working-tree additions cover subscriptions, support, ratings, manual payout records, reports and privacy; their acceptance evidence is recorded separately in PROGRESS.md.

Catalog administration uses `/v1/admin/catalog`; customer catalog/search derives store scope from an owned `addressId` or the default address. An omitted/null price `validFrom` activates at database time after locks. Past requested starts activate at that time without backdating; future starts retain their schedule. Catalog responses use private revalidation with ETags. Local image/capability routes are documented separately from the four audience APIs.

Store stock effects require `Idempotency-Key` (1–150 characters), scoped to actor/store/operation and checked against canonical input. Receipt/quality/approval writes return an empty 201; count/adjustment returns `{}` or `{approvalId}` with identical replay. Administrative stock approval also requires a current store-manager assignment and a checker different from the maker. Error codes include `INVALID_QUANTITY`, `INVENTORY_INSUFFICIENT`, `INVENTORY_RESERVED`, `BATCH_NOT_ELIGIBLE`, `RESERVATION_STATE_INVALID`, `PRODUCT_NOT_PUBLISHABLE`, `INVALID_SEARCH_QUERY`, `APPROVAL_REQUIRED` and `REPORT_NOT_READY`.

The payment webhook is a public HTTP endpoint authenticated by the gateway HMAC signature over the exact request bytes. Its OpenAPI security array is empty deliberately; invalid signatures are durably quarantined and cannot fund an order. Customer verification fetches the provider result; a client signature alone does not establish funding.

Manual rider assignment is limited to pre-pickup custody and requires an admin reason. Financial refunds and the supported cancellation/expiry repairs require separate maker and checker identities. Store COD deposits retain their reference, actual cash and discrepancy; picking reductions change expected collection without rewriting the original order total.

`POST /v1/admin/orders/:id/hold` accepts `{ "held": true, "reason": "..." }` from an active admin or super-admin; set `held` to `false` to resume. It applies to `CONFIRMED`, `PICKING` and `PACKED` orders before pickup. Admin order detail includes current hold details; the customer timeline omits hold reasons. `POST /v1/admin/orders/:id/delivery-code/reset` takes `{ "reason": "..." }` and resets the verifier lock only while the order is out for delivery with assigned, unreleased rider custody; it does not complete delivery.

The rider app uses `GET /v1/rider/status`, `/dashboard`, `/tasks?scope=active`, `/tasks?scope=history`, and `/tasks/:id`. Active task details are restricted to the assigned rider; history is scoped to the rider's assignment attempt and does not expose destination details. The assigned rider records an attempt with `POST /v1/rider/tasks/:id/contact-attempts` and flags an incorrect destination with `POST /v1/rider/tasks/:id/wrong-address` and a reason. Both require `Idempotency-Key`. An admin resolves a flag as failed delivery with `POST /v1/admin/orders/:orderId/wrong-address/resolve`, a reason and `Idempotency-Key`. Customer-unreachable failure and wrong-address resolution require arrival, the configured wait, and the configured number of recorded contacts for the current rider and attempt. A resolved failure retains rider custody pending return. Location ingestion requires an online shift.

Subscription APIs use `/v1/customer/subscriptions`; admin plan/slot/holiday/run administration uses `/v1/admin/subscriptions`. Mutations require an idempotency key. Estimates use normal checkout pricing and minimums; generated orders freeze prices and debit the wallet. Calendar dates and cutoff rules use IST. Schedule changes return the effective date; a named skip/unskip after cutoff conflicts.

Administrators can inspect suspended invoice renders at `GET /v1/admin/invoices/render-failures`. `POST /v1/admin/invoices/{id}/render-retry` requires an `Idempotency-Key` and a `reason`; it records an audit entry and retries the already-issued document without changing its invoice number.

Customer and rider support APIs use `/tickets`, including messages, reopening and scoped private attachments. Support agents use the admin ticket surface; internal notes are excluded from owner views and personal exports. Rating creation/edit lives under delivered orders; authenticated aggregates require the configured minimum number of visible ratings. Moderation is audited.

Payout drafts, approvals, manual settlement and compensating correction records use `/v1/admin/payouts`. A COD offset is distinct from a physical deposit. Zero-net settlement has an internal reference. Positive payments and manual customer refunds require private evidence and stable settlement references. No endpoint initiates a bank transfer.

Admin report previews use `/v1/admin/reports/:kind`; export creation/list/status/download use `/v1/admin/reports/exports`. Customer personal exports use `/v1/customer/me/data-exports`. Jobs expose status and counts; downloads require current owner/role authorization before issuing a short-lived private URL. Catalog and stock are current snapshot reports and reject event-date filters. Financial report activities separate legal documents, order funding, top-ups and refunds; rows must not be summed indiscriminately as revenue.

Existing customer `DELETE /me` requests erasure, with `/me/erasure` showing status while the account remains active. Workforce erasure requires separate administrator approval. Active subscriptions, custody, wallet balance, unresolved money obligations, legal holds and unpaid rider earnings block execution. Local access is revoked before retried external cleanup; financial records retain their anonymized account references. Operational review/replay endpoints use `/v1/admin/ops`, `/fraud-signals`, `/payments/reconciliation` and `/approvals`.

## Admin portal sessions and portal reads (P14)

The DairyDirect admin web portal authenticates with server-side sessions instead of browser-held tokens. `POST /v1/admin/auth/login` verifies workforce credentials against the configured provider (Cognito `ADMIN_USER_PASSWORD_AUTH` on the admin client in production, the local scrypt directory in development), verifies the returned access token for the `admin` audience, authorizes the account and requires the `SUPER_ADMIN` role before creating a session; support agents are rejected with 403 at login. A `NEW_PASSWORD_REQUIRED` challenge returns `{status:'CHALLENGE', challengeId}`; `POST /v1/admin/auth/challenge` completes it. `POST /v1/admin/auth/forgot-password` always answers `{status:'SENT'}` and never reveals whether an account exists; `POST /v1/admin/auth/forgot-password/confirm` answers `RESET` or a generic 400 `INVALID_RESET`. `GET /v1/admin/auth/session` bootstraps the portal (refreshing provider tokens when the access token expired), re-checks `SUPER_ADMIN` and slides the idle window. `POST /v1/admin/auth/logout` revokes the session, optionally every session of the admin with `allSessions:true`, and requires the `x-admin-csrf` header.

Sessions are stored in `admin_sessions`: only the SHA-256 of the raw session id, AES-256-GCM sealed provider tokens (keyed by `ADMIN_SESSION_KEYS_JSON`/`ADMIN_SESSION_KEY_VERSION`), a hashed CSRF token and idle/absolute deadlines. The browser receives only the host-only, HttpOnly, `SameSite=Lax` `admin_session` cookie (Secure except loopback plain-HTTP development) and the raw CSRF token in the JSON body. State-changing portal routes (`challenge`, `forgot-password/confirm`, `logout`) reject cross-site requests whose `Origin`/`Referer` is not in `CORS_ALLOWED_ORIGINS`. Presenting a bearer token and the session cookie together on an admin route is rejected with 409 `CONFLICTING_CREDENTIALS`; cookie-authenticated requests always require `SUPER_ADMIN`, even on routes whose policy also admits support agents. Refresh rotation claims the session row atomically, runs the provider call outside any transaction and rolls the claim back on provider outages; a losing concurrent refresh receives 401 `SESSION_REPLACED` and must re-login. An idle/absolute-expired, revoked or unknown session answers 401 `SESSION_EXPIRED`; provider outages surface as 503.

Portal reads use `/v1/admin/dashboard`, `/v1/admin/delivery/fleet`, `/v1/admin/orders/:id/rider-candidates`, `/v1/admin/orders/:id/invoice`, `/v1/admin/payments/attempts`, `/v1/admin/refunds`, `/v1/admin/inventory/summary`, `/v1/admin/ratings`, `/v1/admin/legal-holds` and `/v1/admin/search`. All require `SUPER_ADMIN`. Dashboard business-day bounds resolve in Asia/Kolkata, accept at most 92 days, and separate issued invoices minus credit notes from processed refunds and captured wallet top-ups; store and customer counts are current snapshots. Fleet rows are bounded, reuse the tracking last-location authority and report a fixed 120-second freshness window. Rider candidates reuse the same eligibility port dispatch revalidates offer candidates with, bounded to the order's store. Invoice downloads answer 404 `INVOICE_NOT_FOUND` or 409 `INVOICE_NOT_RENDERED` and otherwise return a short-lived private URL. Lists are keyset-paginated `{items, nextCursor}` pages with validated filters; global search bounds each entity group to five results and requires 2–64 characters.
