## Admin operational controls — latest working-tree changes

This section records the earlier implementation and verification; the 19 November rollout above supersedes its historical migration and deployment warnings. The implementation has not yet been verified on the owner's phone.

- **Delivery PINs:** Settings → **Delivery PINs** lists, searches, adds and edits six-digit PINs. Each enabled PIN has one assigned store; admins can change the store or disable the PIN. Changes are version-checked and audited. New catalog, cart and checkout decisions use the active PIN assignment immediately, along with store hours and capacity. Existing order snapshots retain their original store. An unknown or disabled PIN cannot place a new order.
- **Location:** The admin feature switch **Require customer location for orders** defaults off if absent. With it off, a complete written address and enabled PIN are sufficient; with it on, the server requires a customer-confirmed location for a new order. The customer app also asks for location services and confirmation at checkout. Refreshing this setting does not overwrite an address being typed. The assistant can save explicitly supplied address details and follows the same policy without inventing coordinates. Maps remain unavailable.
- **Business settings:** Settings → Configuration groups order limits, delivery and handling fees, rider pay and cash limits, delivery timing, support targets, stock warnings, assistant usage and opt-in reminder limits. Store-specific hours, capacity and status continue to be managed in Stores. Settings and PIN changes have an admin-visible history. The Ops tab can check configured dependencies on demand; a configured push provider or worker is not proof of actual message delivery.
- **Admin performance:** The payments and reports pages use a stable date range that refreshes once a minute, preventing a new request on every render while keeping the view current.
- **Stock and wallet:** Inventory → Correct stock lets an admin enter a counted batch quantity and reason, with version checks, reserved-stock protection, audit and retry protection. Payments → Wallet contains a confirmed, reasoned balance adjustment for an existing customer; a single admin can complete it and repeated submissions use the same request key. If a confirmation has expired without being applied, the admin can explicitly confirm a fresh request. Promo credits and debits now update their spendable lots as well as the ledger and account balance. This does not add customer wallet top-ups. Historic promo adjustments created before this fix are not automatically repaired and should be reviewed separately before relying on those balances.
- **Rider distance:** If a delivery has no usable distance, base pay, eligible waiting pay and tips remain recorded; the distance portion is marked for review. Payouts → distance reviews lets an admin record a distance and reason. The additional amount uses the rate captured at delivery and enters a subsequent payout once, including when base earnings were already paid. Recording it does not itself transfer money.
- **Product scope:** Cash on delivery and existing wallet balances remain the available payment methods; online payment is blocked by default and presented as coming soon. Maps, wallet top-ups, subscriptions and recipes remain unavailable for this testing scope. Reorder nudges remain opt-in.

### Priority findings for the next implementation pass

1. **Refund completion and permission:** fix the approved-draft lifecycle above. `stageDecision` checks permission before the separate support transaction, but the refund ticket's `beforeCreate` guard only checks the draft and does not recheck `requireAgentPermission`. Verify consent and the feature switch again inside the ticket transaction, including concurrent revocation/disable, duplicate approval and crash/retry cases. Treat the current conclusion as a code-path finding until an integration test reproduces it.
2. **Nudge history and delivery:** `AgentNudges.sweepUser` calls `orders.list`, whose list results have `items: []`; `historyFromOrders` consequently sees no purchase history and the worker returns without a candidate. The existing nudge integration suite stubs populated order items, so its passing result does not verify this real cross-module path. Once item data is fixed, count delivered purchases only and check active-order suppression; the current history filter only excludes `CANCELLED` and `EXPIRED`. Test through the real order service and outbox using isolated data.
3. **Nudge scheduling and navigation:** the sweep can repeatedly select the same first 50 preferences; it checks notifications before outbox consumption and emits fresh aggregate IDs, so overlapping/delayed sweeps need durable deduplication and cap tests. Its seven-day query is user-wide rather than variant-specific. Verify opt-in/opt-out, consent withdrawal, quiet hours, notification preferences and ignored-nudge stopping. The newer completion-alert handler recognizes `/agent` only when a thread ID is present; reorder-nudge payloads do not currently provide one, so their tap path still reaches the profile notifications panel and the assistant has no prefilled-nudge path. Test push and inbox navigation without auto-sending a message.
4. **Cards and address:** `AssistantCard` renders usual-order items without selection or quantity controls; `AgentActions` only accepts `add_to_cart` with quantity one. Its replay key is based on card and variant, so a later deliberate second tap on the same item is treated as the original action. Provide distinguishable intentional actions while retaining double-tap safety; test selection, quantity changes and stale/forged cards. Show recent order number/status and the authoritative ETA on confirmation where available. Localise currently hardcoded card titles/descriptions in English, Hindi and Telugu.
5. **Tool descriptions and scope:** `get_order_history_summary` tells the model to obtain a quote before `place_order`, but no separate `get_quote` tool is registered; `place_order` obtains the checkout quote internally. The customer action contract supports only `add_to_cart`, while the prompt also describes other actions. Coupons and substitutes remain explicitly deferred, not silently marked implemented.
6. **Streaming and errors:** the client sends an `Accept` header containing `text/event-stream`; the server therefore streams, and the client throws `STREAM_UNAVAILABLE` when no body is available instead of retrying with `application/json`.
