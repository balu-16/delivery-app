# DairyDirect admin and store-manager customization

## 1. Outcome and product decisions

An admin must be able to set up a store, publish a product with photos and pricing, change order and delivery rules, manage promotions, accept rider applications, send notifications, and publish customer and delivery-partner content from the portal. A successful save must persist on the server and affect the intended app or workflow on its next relevant read. Store managers need the controls to operate their assigned stores each day.

Use `milk_admin`, `milk_store`, `milk_customer`, `delivery_partner_app`, and `server`. `milk_store` is the full store operations frontend. The root README also links to the smaller `server/store_manager_web` client for picking and rider reviews. Keep its existing store API calls compatible and use `milk_store` for feature acceptance. Record the portal and backend URLs used for acceptance. The target actually deployed has yet to be verified. [Full store portal guide](milk_store/README.md) · [Smaller store portal guide](server/store_manager_web/README.md)

| Decision | Required behavior |
| --- | --- |
| Admin authority | An active `SUPER_ADMIN` manages all stores and business settings, workforce assignments, catalog, prices, money and policy exceptions, campaigns, app content, and rider reviews. Use the existing single database role and matching workforce identity group. Use the existing audited role-change flow for promotion to `SUPER_ADMIN`. |
| Store manager authority | An active `STORE_MANAGER` can manage inventory and routine adjustments, picking and packing, handover, returns, COD deposit recording, staff workload, rider document review, and manager-controlled pauses at assigned stores. The manager can manage their own inbox preferences. Admin owns hours, holidays, capacity, listings, pricing, COD policy, assignments, and account roles. |
| Rider applications | An admin can review applications across stores. A manager can review applicants at an assigned home store. Either can complete the review. The application becomes `APPROVED` when its latest documents satisfy all requirements for that review. |
| Commercial model | Each variant has one effective selling price and MRP shared by all stores. Availability belongs to each store. An item discount can be represented by selling below MRP. Date-limited promotions use the existing coupon validity windows and scope rules. Delivery charges configured here are platform-wide. Store eligibility, hours, and COD availability are per store. |
| App customization | Editable app content covers the customer home banner and offers card, a rider home announcement, and help copy in both apps. The backend owns the content, and the apps render it in their existing layouts. Campaigns use immediate push delivery. Existing automated notifications continue to use their channels and event rules, with editable message copy. |
| Lifecycle constraints | Previously placed orders, invoices, confirmed payouts, earned referral credits, and historical messages retain their recorded values. Honor the existing retirement of recurring subscriptions and the current wallet top-up availability. Admin and store-manager access use the current portal sessions. A support-only portal is a separate scope. |

## 3. Build sequence

### A. Access, stock approval, and store status

**Portal sessions.** Apply CSRF validation for authenticated cookie writes in `IdentityGuard` after establishing the matched session. Use the admin session store and `x-admin-csrf` for admin, and preserve the store session store and `x-store-csrf` for store. Keep the existing failure envelope and return `403 CSRF_TOKEN_INVALID` before a mutation is executed. Leave login, password challenge, and other authentication bootstrap flows on their existing contracts. Bearer requests continue to use token audience and role authorization. Share the same implementation for header parsing and session verification where the behavior matches. Update the admin client's HTTP wrapper to refresh `/v1/admin/auth/session` and retry once on the explicit pre-execution stale-CSRF response, retaining the original body and idempotency key. Make concurrent callers share that refresh. Continue to handle expired sessions through the existing sign-in flow. Test a session rotation, an ineligible role, an expired session, and a missing CSRF token. [Identity guard](server/src/modules/identity/contracts/identity-guard.ts) · [Admin HTTP client](milk_admin/src/api/http.ts) · [Store HTTP recovery](milk_store/src/api/http.ts)

**Manager store scope.** Preserve the `/v1/store` audience and check the live assignment on server reads and mutations. Derive the store from a referenced task, batch, return, deposit, or rider application before authorizing. When a request supplies both a store and a resource ID, validate the relationship. Keep the transaction-scoped role checks on writes so revoked assignments, blocked users, and stale sessions cannot commit new work. Verify both the collection and ID-based routes for all store operations. Monitor manager permissions through the shared contracts and tests, with the portal navigation reflecting those permissions. [Store operations controllers](server/src/surfaces/store) · [Store assignment checks](server/src/modules/identity/infrastructure/identity-access.ts)

**Stock approvals.** An assigned manager submits a count or adjustment with the existing reason, inventory version, and idempotency reference. The server applies deltas up to and including `inventoryAdjustmentApprovalUnits` and produces a pending approval for a larger absolute delta. Return the threshold in the authorized store inventory read so the dialog can explain the rule. Use the server result as the authority for pending status, including when the threshold changes between read and submit. Remove the hardcoded 20 and keep pending, rejected, stale, and executed states visible on the store side. [Threshold rule](server/src/modules/inventory/infrastructure/count-claim.ts) · [Manager UI](milk_store/src/pages/StoreInventory.tsx)

- Move `INVENTORY_COUNT` to a new action version with `STORE_MANAGER` as maker and `SUPER_ADMIN` as checker. Keep a current assignment check for the maker at execution, validate the original store, batch, variant, version and count payload, and authorize the active admin checker independently of store assignment. Use the existing admin inventory approval route and central reject route. A manager can submit or view an assigned-store request. Require admin authorization to execute the gated adjustment and return a clear denial on the legacy store approval route. Preserve the approval behavior for unrelated action types.
- Reuse `MakerChecker`, the idempotency reference, and the existing inventory locks. Double-click and concurrent admin approval must result in one inventory movement and one checker decision. Retrying the same successful approval is safe. A rejected, expired or conflicting request must have a clear terminal or conflict state. The admin-facing approval query should expose server-calculated `canApprove`, `canReject`, and a reason when a decision is unavailable. Use those values in the Approvals page and still recheck the policy during execution.
- Coordinate the approval cutover across all inventory writers. During the cutover, quiesce approval creation and execution, migrate unexpired pending `INVENTORY_COUNT` rows to the new `action_version` and `required_role` under the existing approval lock, and record the migration in audit history. Preserve their IDs, original maker, payload, hash, expiry, and execution reference. Historical terminal decisions retain their original authority. Verify new and legacy pending requests before reopening the flow. Use a dedicated data migration and leave already-applied migrations intact.

**Manual and automatic store pauses.** Add nullable `source` to `store_status_history` for `ADMIN`, `MANAGER`, and `SYSTEM`. Write it from both manual status handlers and both automatic pause producers. Decide available actions from the latest status-history row under the same store lock as the transition, even if capacity or COD settings raised the store version since the pause. Admin can activate an `OFFLINE` store, pause or resume any store, and take ownership of an existing pause by recording an admin pause. Managers can pause an `ONLINE` assigned store with a reason, and resume an assigned store whose latest actual pause is manager-controlled. Treat legacy paused rows with unknown source as admin-controlled. Return `canPause`, `canResume`, and a restriction reason on the store status read. Use the same capabilities in Dashboard and Store Status. Preserve status history and customer serviceability checks. Cover a manager pause overwritten by an admin pause, automatic pauses, simultaneous changes, and a paused store with active orders already underway. [Status writer](server/src/modules/stores/infrastructure/store-status.ts) · [Automatic pause writers](server/src/modules/stores/infrastructure/store-signals.ts)
